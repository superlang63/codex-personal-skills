# Debug 模式

## 核心原则

使用运行时证据定位根因，不猜测式修改。先观察，后修复；先证明根因，再实施最小变更。

始终区分：

- **事实**：代码、日志、堆栈、测试或可重复实验直接证明的内容。
- **假设**：尚待验证的根因解释。
- **结论**：已有证据支持且替代假设已被合理排除的判断。

如果用户只要求诊断或解释，止于根因分析和修复建议，不修改代码。用户明确要求查找并修复时，完成整个工作流。

## 与 Vibe Grilling 联动

开始调试时检查仓库是否存在 `PROJECT_LEDGER.md`、`CHANGE_PROPOSALS/` 或其在 `DOCUMENT_MAP.md` 中登记的等效文档。若当前缺陷能够唯一关联到一个由 `vibe-grilling` 管理的活动任务,则执行以下规则:

1. 记录当前 `task_id` 和 `proposal_id`;无法唯一关联时先询问用户,不得猜测。
2. 调试过程中维护证据账本,并在阶段性结论形成时同步更新对应提案的「调试记录」。
3. 至少记录问题现象、复现步骤、根因假设、支持证据、反证、确认根因、修复、验证、临时插桩清理和剩余风险。
4. 未验证内容标记为「AI 未验证」或「待验证」,不得把假设写成结论。
5. 调试完成或暂停时更新当日 `SESSION_LOG`;任务状态变化时在同一轮更新 `PROJECT_LEDGER.md`。
6. 若根因要求突破已确认提案范围,停止实现并按 `vibe-grilling` 规则建立替代提案,等待用户重新确认。
7. 仅回写与当前任务相关的调试内容,不得记录密钥、令牌、完整个人信息或其他敏感数据。

若不存在活动治理任务,正常执行 Debug 工作流,不擅自创建 `vibe-grilling` 文档。

## 阶段 1：建立基线

1. 阅读仓库规则、相关代码、配置、测试和近期变更，不覆盖用户已有修改。
2. 收集预期行为、实际行为、错误信息、堆栈、环境、出现频率和最短复现步骤。
3. 尽可能先复现一次，并记录原始失败结果；无法复现时明确说明缺失条件。
4. 检查问题描述是否包含错误前提、逻辑跳跃或信息缺口。
5. 输出简短状态：已知事实、未知信息、复现状态和下一步。

不要因为看到可疑代码就立即修改。明显的编译错误或确定性缺陷也要记录其证据。

## 阶段 2：探索并提出假设

沿调用链、数据流、状态变化、线程或异步边界检查相关实现。提出两个到五个彼此可区分的假设，并维护证据账本：

| 假设 | 支持证据 | 反证 | 验证方法 | 状态 |
| --- | --- | --- | --- | --- |
| 根因候选 | 已观察事实 | 冲突事实或暂无 | 最小实验或插桩点 | 待验证/排除/确认 |

优先验证同时满足“解释力强、验证成本低、对代码扰动小”的假设。每次实验只改变一个主要变量，避免多个修改混淆结论。

## 阶段 3：添加临时插桩

只添加能区分当前假设的最小插桩，例如：

- 关键分支、输入输出和状态转换日志；
- 时间戳、请求或任务关联标识、线程或异步上下文；
- 计数器、耗时、内存或资源生命周期信息；
- 临时断言或针对性诊断测试。

插桩要求：

- 使用醒目的统一标记，例如 `[DEBUG-MODE]`，便于最终完整删除。
- 记录足够上下文，但不得输出密码、令牌、密钥、完整个人信息或敏感业务数据。
- 避免改变时序；调查竞态时评估日志本身对复现概率的影响。
- 不在高频路径制造无界日志，不把临时诊断代码混入无关重构。
- 记录新增插桩的文件和位置，形成清理清单。

若现有日志、测试输出、调试器或分析器已经能提供所需证据，优先复用，不强行改代码。

## 阶段 4：指导复现并分析证据

向用户提供精确、编号化的复现步骤，说明需要执行的命令、操作、次数和应返回的日志。必须等待真实运行结果，不虚构执行结果。

收到结果后：

1. 将日志按关联标识、时间和调用顺序还原为事件链。
2. 更新证据账本，逐项确认或排除假设。
3. 检查日志缺口、采样偏差、环境差异和不可重复性。
4. 证据不足时调整插桩并再次复现；竞态问题通常需要多次运行。
5. 只有当证据解释实际行为并指向具体机制时，才宣布根因已确认。

如果必须由用户在图形界面、设备、外部服务或特殊环境中操作，把“等待复现”作为明确阶段门禁，不提前修复。

## 阶段 5：实施定向修复

根因确认后：

1. 说明根因机制、关键证据和拟修改范围。
2. 实施直接解决根因的最小变更，避免顺手重构和无关格式化。
3. 遵守项目架构、注释、日志、错误返回和测试目录规范。
4. 为已确认的缺陷补充最小回归测试；无法自动化时说明原因。
5. 保留临时插桩直到修复验证完成，以便比较修复前后证据。

若修复会改变公共接口、数据结构、数据库、兼容性或安全策略，先说明影响并取得必要授权。

## 阶段 6：验证并清理

1. 按原始步骤重新复现，证明实际行为符合预期。
2. 运行最相关的测试、静态检查或构建；区分原有失败与本次回归。
3. 必要时重复运行，验证竞态、性能或资源问题不是偶然消失。
4. 删除清理清单中的全部临时日志、断言、诊断开关和辅助文件。
5. 删除后再次运行关键验证，确保清理没有破坏修复。
6. 检索 `[DEBUG-MODE]` 等标记，确认没有遗留插桩。

未经验证不要声称“已修复”。验证受环境限制时，明确说明已验证内容、未验证内容和剩余风险。

## 最终报告

用简洁结构交付：

- **根因**：导致缺陷的具体机制。
- **证据**：复现、日志、堆栈或测试如何证明根因。
- **修复**：修改了什么以及为何是最小修复。
- **验证**：执行的命令或步骤及结果。
- **清理**：临时插桩是否已全部删除。
- **剩余风险**：未覆盖环境、偶发性或后续建议。

除非用户明确要求，不提交或推送 Git，不扩大任务范围。
