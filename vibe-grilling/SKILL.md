# Vibe Grilling

把模糊的想法拷问成一份用户确认过的变更提案,再动手实现;全程留痕、可追溯。

一句话:**先问透,再落盘,过关卡,才动手,必还账。**

完整工作流是一条流水线:

```
拷问(问清决策) → 提案(共识落盘) → 关卡(用户确认) → 实现 → 验证 → 还账(台账 + 会话摘要)
```

## 适用范围

- 新项目启动:建立台账骨架,拷问产品目标与技术边界。
- 新功能 / 新任务开工:拷问需求口径,产出变更提案。
- 方案确认前:用户想先把事情想清楚再动手。
- 接手已有项目:先读现状,建立映射,不推翻既有目录。

琐碎改动不走全流程,见「快速通道」。

## 阶段一:拷问

原则:

1. **一次只问一个问题**,得到回答后再问下一个。一次抛出一串问题只会让人晕头转向。
2. **每个问题附上你的推荐答案**和理由,让用户可以只回「同意」。
3. **事实自己查,决策问用户。** 能从代码、文档、环境里查到的事实(现状、依赖、已有实现)不要问;方案取舍、产品范围、优先级这些决策必须交还给用户。
4. 沿决策树逐枝推进:先解决被依赖的决策,再解决依赖它的决策。
5. 被否决的选项连同否决理由一起记录,后面写进提案的「已否决」小节。

拷问深度分级:

- **全程拷问**:任务命中任一关卡条件(见阶段三),或用户明确要求 grill。
- **快速确认**:不命中关卡条件的中小改动,只问 1~3 个关键问题,确认口径后直接进提案。

拷问的终点不是「问完了」,而是你能用一段话向用户复述出:要做什么、不做什么、关键取舍是什么、怎么验证。用户确认这段复述,即为共识达成。

## 阶段二:提案落盘

共识达成后,立即把它结晶为一份变更提案,写入 `CHANGE_PROPOSALS/<proposal_id>-<短标题>.md`:

```markdown
# 提案 <proposal_id>:<标题>

- task_id: <台账任务 ID,如 3.1>
- 状态: 待确认
- 日期: YYYY-MM-DD

## 背景与动机
<为什么做这件事>

## 已确认的决策
<拷问中拍板的决策,逐条列出>

## 已否决
- <选项> —— <否决理由>

## 变更范围
<预期新增 / 修改 / 删除的文件清单>

## 风险与回退
<风险点;出问题怎么回退>

## 验证步骤
<实现完成后按此逐条验证>
```

规则:

- **一个提案只管一个主题。** 一个任务可以拆多个提案,不要把不相关的变更塞进同一份。
- 实现过程中范围变了:当前提案标记为「已废弃(被 #<新 id> 取代)」,为新范围开新提案,不允许在旧提案里偷改。
- 提案落盘后把路径抛给用户,等待关卡确认。

## 阶段三:确认关卡

命中以下任一条件,必须先有经确认的提案才能动实现(调查现状、读代码、写提案可以先做):

- 需求口径不完整,或存在多个合理实现方向;
- 改变产品范围、权限、安全边界、公开 API 或兼容性;
- 引入新的外部服务或依赖;
- 变更影响难以回退;
- **任何数据库表、DDL、迁移或等效 ORM schema 变更**——提案里必须单独标注。

关卡只有一种通过方式:用户对提案明确说「确认 / 同意 / 就这么做」。沉默或模糊回应不算通过。用户拒绝则把拒绝理由记录进提案并标记「已拒绝」,再询问是否调整方向重新拷问。

## 快速通道(琐碎改动豁免)

同时满足以下条件时,可跳过提案与关卡,直接实现:

- 不改公开接口、schema、权限、安全边界;
- 单点小修(改文案、修明显笔误、局部样式),一处提交内可轻松回退;
- 不引入新依赖。

仍须在会话摘要里记录做了什么、为什么。

## 阶段四:实现、验证、还账

1. **实现**:严格按提案的变更范围动手,不夹带。
2. **验证**:按提案的「验证步骤」逐条执行;跑测试、构建或实际调用验证。
3. **还账(与状态变更同一轮完成,不许拖到最后)**:
   - 更新 `PROJECT_LEDGER.md`:任务状态推进;
   - 写 `SESSION_LOG/<日期>-<主题>.md`:task_id、proposal_id、做了什么、下一步、动过的文件。

台账规则:

- 任务用唯一 ID 组成任务树(如 `3.1`、`3.1.2`),**只增不删**;作废的任务标 DEAD,不删除。
- 状态只取五个值:PENDING / IN_PROGRESS / IN_REVIEW / DELIVERED / BLOCKED。
- **状态变更与台账更新必须在同一轮完成**——这是防止台账与现实漂移的硬规则。

## Debug 联动留痕

当前需求进入本技能治理后,只要后续任何一轮使用过 `$Debug` 或 `debug-mode`,就必须把与当前 `task_id` / `proposal_id` 有关的调试活动回写到治理文档。无需每轮同时再次调用本技能。

关联与记录规则:

1. 调试开始时先识别当前任务和有效提案;无法唯一关联时先询问用户,不得猜测归属。
2. 在对应 `CHANGE_PROPOSALS/<proposal_id>-<短标题>.md` 维护「调试记录」,至少包含问题现象、复现步骤、根因假设、证据与反证、确认根因、修复方案、验证结果、临时插桩清理状态和剩余风险。
3. 事实、假设和结论必须分开;尚未由运行时证据验证的内容标记为「AI 未验证」或「待验证」。
4. 在 `SESSION_LOG/<日期>-<主题>.md` 记录本轮使用了 Debug、关键证据、结论、修改文件、验证结果和下一步。
5. 调试引起任务状态变化时,在同一轮更新 `PROJECT_LEDGER.md`。
6. 调试发现原提案范围不成立时,不得偷改已确认范围;将原提案标记为「已废弃(被 #<新 id> 取代)」并建立新提案,重新经过确认关卡。
7. 与当前任务无关的 Debug 活动不得写入当前提案。敏感数据、密钥、令牌和完整个人信息不得进入治理文档。

推荐的提案章节:

```markdown
## 调试记录

### 问题现象与复现
### 根因假设
### 证据与反证
### 根因结论
### 修复与验证
### 临时插桩清理
### 剩余风险
```

## 文件布局(按需创建)

```
<仓库根目录>/
├── PROJECT_LEDGER.md      # 项目总进度台账(首次开工时创建)
├── CHANGE_PROPOSALS/      # 变更提案,一提案一文件
├── SESSION_LOG/           # 会话摘要,一会话一文件
└── DOCUMENT_MAP.md        # (可选)模板职责 → 项目真实文档路径的映射
```

不要一上来铺满所有文件。项目里已有 PRD / 设计文档 / specs 目录的,优先沿用既有目录,在 `DOCUMENT_MAP.md` 里登记映射;什么都不建的微小项目,至少维护台账与提案。

文档纪律:文档只描述已验证的现状,不描述承诺;AI 尚未验证的内容必须标注「AI 未验证」。

## 首次接入已有项目

1. 先调查现状:读目录结构、README、已有文档,查清已有的近似规范。
2. 已有近似的台账 / 提案体系 → 沿用,把本技能的职责映射过去,不推倒重来。
3. 没有 → 征得用户同意后创建最小骨架(`PROJECT_LEDGER.md` + `CHANGE_PROPOSALS/`),把现状盘点为首批任务。
